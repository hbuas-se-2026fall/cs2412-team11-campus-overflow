# ADR-003 核心特性设计：投票、采纳、评论、标签与声誉

- 状态：已采纳
- 日期：2026-11-28
- 决策人：第 11 组全体
- 相关模块：co-qa、co-reputation、co-identity

## 背景

Sprint 3 需要在问答主链路上补齐互动能力：对问题和回答投票、提问者采纳答案、
对问题和回答评论、按标签归类与筛选、并根据互动计算用户声誉。

这些能力横跨三个限界上下文：co-qa（问题、回答、投票、评论、标签）、
co-reputation（声誉账本与排行榜）、co-identity（用户与角色）。

## 决策

### 1. 投票采用「一人一票、可改票、可撤销」

- 数据模型：`qa_vote` 以 `(target_type, target_id, user_id)` 唯一约束记录当前票值。
- 票值域：`-1 / 0 / 1`，其中 `0` 表示撤销。
- 同一用户重复投票是覆盖而不是累加，避免刷票。
- 聚合内校验：不能给自己的内容投票、未登录不能投票。

### 2. 采纳由提问者独占，且只能采纳一个答案

- 接口：`PUT /api/v1/questions/{questionId}/accepted-answer`，body `{ answerId }`。
- 权限：仅提问者本人可采纳；管理员不代行，避免争议。
- 不变式：一个问题最多一个被采纳答案；换采纳时原答案自动取消。
- 答案聚合标记 `accepted`，问题侧记录 `acceptedAnswerId`。

### 3. 评论独立聚合，通过 targetType 关联

- 接口：`POST /api/v1/comments`，body `{ targetType, targetId, parentId, body }`。
- `targetType` 只有 `QUESTION` 和 `ANSWER` 两个值。
- 评论不参与声誉计算主干，只作为讨论补充，正文上限 600 字符。

### 4. 标签采用「问题侧引用 + 标签侧统计」

- 问题发布时携带 1~5 个标签，落库在 `qa_question_tag`。
- 热门标签由 `GET /api/v1/tags/popular` 按问题数倒序返回。
- 按标签筛选走 `GET /api/v1/search/questions?tag=...`，而不是给问题列表接口
  硬塞参数，保持列表接口职责单一。

### 5. 声誉通过领域事件异步结算

- co-qa 在投票、采纳发生时发布领域事件（outbox 表保证可靠投递）。
- co-reputation 订阅事件，写入 `rep_ledger`，再汇总成账户余额。
- 排行榜由账户余额排序产生，`GET /api/v1/leaderboard?period=week|month|all`。
- 为什么异步：声誉不是互动主链路的强一致需求，异步可避免投票接口被声誉
  计算拖慢，也让声誉规则可以独立演进。

## 备选方案与取舍

| 备选 | 否决原因 |
|---|---|
| 投票累加而不是覆盖 | 同一人反复点击即可刷分 |
| 允许多人采纳或管理员采纳 | 语义混乱，争议无法仲裁 |
| 评论直接用一张多态表 + 外键 | 破坏模块边界，co-qa 无法独立演进 |
| 声誉同步写在投票事务里 | 跨上下文强耦合，任一模块故障会阻塞投票 |
| 给 `GET /questions` 加 tag 参数 | 与搜索语义重叠，接口职责不清 |

## 后果

- 正向：互动能力边界清晰，三个上下文可独立测试与部署。
- 正向：声誉具备可追溯的账本，便于审计与回滚。
- 负向：声誉存在短暂延迟（事件投递到结算完成），排行榜可能滞后数秒。
- 负向：评论与标签拆成独立聚合后，详情页需要聚合多次查询，读侧复杂度上升。
